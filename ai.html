AI

Backend structure for work that runs unattended — queues, workers, and machines that hand jobs to each other.

The model call is the cheap part. The expensive part is getting work queued in the right order, onto the right machine, in a process that cannot take the rest of the batch down with it, with something at the end that checks the result was real. The bias throughout is toward boring, inspectable mechanisms: the filesystem instead of a message broker, a directory name instead of a status column, an exit code instead of a model's opinion that it succeeded.

a queue where the directory is the status

Queue diagrams and run logs, once uploaded.

A job is a file. A worker claims it by moving it, does the work, and moves it again to record what happened — so there is no server, no daemon, and nothing to inspect or recover that ordinary file operations cannot reach. The move is atomic, so two workers cannot take the same job.

 pending --claim--> claimed --> done
                       |
                       +------> failed --retry--> parked

Parking is the part that earns its keep: a job that keeps failing neither blocks the queue nor disappears. The run continues without it and it is still there to look at afterwards.

one process per job

Batch output to come.

Every job gets its own process and its own timeout. Thirty scenes opened in one shared interpreter will not finish thirty — one of them hangs, or cooks forever, or takes the interpreter down without raising anything catchable, and the run dies partway with no clear sign of which input killed it. Isolated, that same failure costs one job and a log entry. The price is paying process startup thirty times, and it is worth it.

routing work to the machine that can do it

Topology diagram to come.

Two machines over a private network, with a deliberate asymmetry. Work needing more model than the laptop has goes to the desktop as one of two commands, and the split is a safety boundary rather than a convenience — the thinking one has no tools bound to it at all, so it can answer but cannot touch a filesystem; the acting one produces a plan and does nothing until told to commit.

 laptop                     desktop
 +--------+  think ------>  no tools bound   (answers only)
 | orch.  |  act   ------>  executor         (plan unless committed)
 +--------+
     +--> unreachable = exit non-zero, never a silent fallback

The failure mode is the design. If the far machine is unreachable the command errors out rather than quietly dropping to the smaller local model, because an answer from something that could not have answered the question is worse than no answer.

agents as workers

Controller output to come.

Model tiers are workers and a controller hands them tasks. Each task declares what it depends on and, more importantly, how to prove it worked: a command that runs after the worker reports finished, whose exit status decides whether the task is done. A worker claiming success is evidence of nothing. Roles are enforced where work is dispatched rather than requested in a prompt, so a tier cannot quietly take another's job.

The rest is unhappy paths, and all of it came from watching real runs fail. Bad verification commands are rejected when the task is queued, not discovered hours later. A dead worker is relaunched once, and if it fails again its task parks and the loop keeps going. One controller at a time, enforced with a lock. Crashed runs clean themselves up on the next start. Long batches are scheduled against a hardware wake timer — the machine wakes itself, works the queue, and sleeps — which is only safe because of everything above.

an agent that looks at what it just did

Session frames to come.

Applied to game and interface work, the verification idea gets more interesting, because the thing you want to check is not a number or an exit code — it is whether the screen looks right. So the loop closes visually: build the thing, run it, capture frames of it running, and hand those frames to a model that reads them back and reports what is wrong with the layout. A proposed fix is applied, and then the same loop runs again to decide whether the original complaint actually went away. Checking the fix is treated as a separate step from making it, for the same reason a worker reporting success is not evidence anywhere else in this system.

Around that sit the ordinary but necessary parts: sessions that persist so a long run can be stopped and resumed, checkpoints written without blocking the work in progress, and cheaper and stronger model tiers configured for different steps rather than one model doing everything. It is the oldest piece here and the least tidy — it depends on a shared component kept outside the project, so it is a design worth describing rather than something to pick up and run.

 build --> run --> capture frames --> model reads the frames
   ^                                          |
   |                                    proposed fix
   |                                          |
   +---------------- apply -------------------+
              then re-check, as its own step

controlling one machine from another

Session capture to come.

The most complete version of the two-machine idea is a pair of programs that let a laptop drive a desktop as if sitting at it. One side captures the screen, compresses it to video, and sends it; the other shows it in a window and sends keyboard, mouse and clipboard back over the same connection. Written in Go, using the operating system's own capture path and a hardware video encoder, because a remote screen is only useful if it keeps up.

Security is built in rather than added later, on the reasoning that this is a program whose entire purpose is letting one computer type into another. The connection is encrypted and the client checks it is talking to the machine it expects by fingerprint, aborting before any data moves if that does not match. Sessions are authenticated with a long random token compared in constant time, only one client may hold control at a time, an idle connection is dropped, and incoming input is rate-limited so a flood cannot be used to hammer the far machine. Where something is deliberately not done yet — rotating the session token, for one — it is written down as such rather than implied to be finished.

how this is put together

Every stage has an observable state and an objective way to tell whether it worked. Status is where a file lives, not a variable someone has to keep updated. Verification is an exit code, not a claim. Failure is bounded to one job. Recovery happens on the next start instead of requiring a person. None of it is specific to models — it is ordinary batch-system design — but it is what makes a model something you can put in a pipeline rather than something you sit and watch.

Scope, plainly: systems and orchestration around models — scheduling, routing, isolation, verification. Not model training, and no computer-vision work.
