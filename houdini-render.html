Rendering and cataloguing

A file-based render queue and a tool that opens old Houdini scenes and records what they contain.

Overview AI inside Houdini Houdini and ComfyUI Rendering and cataloguing Houdini to Bambu Studio

Render job queue

The queue has no server. Each job is a file, and the folder that holds it is its status.

 pending > claimed > done
              |
              +----> failed
              |
              +----> parked (held by an operator)
  • Claim. A worker claims a job with an atomic rename, so only one worker can win it.
  • Isolation. Each job runs in its own headless process with a time limit. A scene that hangs or crashes fails only its own job.
  • Recovery. A sweep returns jobs from dead workers to the queue. A recovered job can render twice, by design.
  • No render node. If a job names no render node, the worker fits a camera and renders a preview. This shows if a scene renders at all. It does not replace an artist's setup.

In the end-to-end test, a worker claimed a job, rendered a real test frame in 12.3 s, and wrote the result. Queue rules pass 20 of 20 checks.

Limit: the system has run on one machine only. The two-machine claim over a network share is a design argument and has not been tested.

Scene cataloguer

Old scenes can hang, crash, or need missing files. The cataloguer opens each scene in its own bounded headless process. It writes a thumbnail and a structured summary, and then merges the results for the site grid.

  • Display flag rescue. If a display flag cooks to nothing, the tool finds the best end of the node chain. This rescued 4 scenes from empty images.
  • Camera fit. The camera fits the smaller of the two fields of view, and then tightens to 88% fill against the real bounds.
  • Curation. Of 30 scenes probed, 13 are in the catalogue and 6 are on the 3D Work page.

End-node captures

This mode takes one labelled viewport image of every end node of every scene. In Houdini 22, a second headless OpenGL render in one process crashes it, so each image gets its own process. Progress is saved per scene, so a stopped run continues where it ended.

State: 101 scenes and 367 images are done. The run is paused at scene 102 of 439. Scenes with over 1000 nodes used too much memory on a 16 GB machine, and a per-process memory limit is not built yet.

API check before code

Houdini's Python API has many names that look correct and do not exist. A small tool asks a real Houdini what a call or parameter is named before any code uses it.

렌더링과 카탈로그

파일 기반 렌더 큐, 그리고 오래된 후디니 씬을 열어 그 내용을 기록하는 도구.

개요 후디니 속 AI 후디니와 ComfyUI 렌더링과 카탈로그 후디니에서 Bambu Studio로

렌더 작업 큐

큐에는 서버가 없습니다. 작업 하나가 파일 하나이고, 그 파일이 들어 있는 폴더가 곧 상태입니다.

 pending > claimed > done
              |
              +----> failed
              |
              +----> parked (held by an operator)
  • 할당. 워커는 원자적 이름 변경으로 작업을 가져가므로, 한 작업은 워커 하나만 차지할 수 있습니다.
  • 격리. 각 작업은 시간 제한이 있는 자체 헤드리스 프로세스에서 실행됩니다. 멈추거나 충돌하는 씬은 자기 작업만 실패시킵니다.
  • 복구. 정리 과정이 죽은 워커의 작업을 큐로 돌려보냅니다. 복구된 작업은 설계상 두 번 렌더될 수 있습니다.
  • 렌더 노드 없음. 작업에 렌더 노드가 없으면 워커가 카메라를 맞추고 미리보기를 렌더합니다. 씬이 렌더되는지 여부를 보여줄 뿐, 아티스트의 설정을 대신하지 않습니다.

처음부터 끝까지 테스트에서 워커가 작업을 가져가 실제 테스트 프레임을 12.3초에 렌더하고 결과를 기록했습니다. 큐 규칙은 검사 20개를 모두 통과합니다.

한계: 이 시스템은 컴퓨터 한 대에서만 실행되었습니다. 네트워크 공유를 통한 두 대 간의 작업 할당은 설계상의 주장이며, 테스트하지 않았습니다.

씬 카탈로거

오래된 씬은 멈추거나, 충돌하거나, 없는 파일을 필요로 할 수 있습니다. 카탈로거는 각 씬을 제한된 자체 헤드리스 프로세스에서 엽니다. 썸네일과 구조화된 요약을 쓰고, 결과를 합쳐 사이트 그리드를 만듭니다.

  • 디스플레이 플래그 구조. 디스플레이 플래그가 아무것도 만들지 않으면, 노드 체인에서 가장 알맞은 끝을 찾습니다. 이 방법으로 빈 이미지였던 씬 4개를 살렸습니다.
  • 카메라 맞춤. 카메라는 두 시야각 중 작은 쪽에 맞춘 뒤, 실제 경계에 대해 88% 채움으로 좁힙니다.
  • 선별. 검사한 씬 30개 중 13개가 카탈로그에 있고, 6개가 3D 작업 페이지에 있습니다.

엔드 노드 캡처

이 모드는 모든 씬의 모든 엔드 노드마다 라벨이 붙은 뷰포트 이미지를 하나씩 찍습니다. 후디니 22에서는 한 프로세스에서 두 번째 헤드리스 OpenGL 렌더를 하면 충돌하므로, 이미지마다 프로세스를 따로 씁니다. 진행 상황은 씬마다 저장되므로, 멈춘 실행은 끝난 곳에서 다시 이어집니다.

상태: 씬 101개, 이미지 367장이 완료되었습니다. 실행은 439개 씬 중 102번째에서 일시 정지되어 있습니다. 노드가 1000개가 넘는 씬은 16 GB 컴퓨터에서 메모리를 너무 많이 썼고, 프로세스별 메모리 제한은 아직 만들지 않았습니다.

코드 전에 API 확인

후디니의 Python API에는 맞아 보이지만 실제로 존재하지 않는 이름이 많습니다. 작은 도구가 코드에서 쓰기 전에 실제 후디니에 호출이나 파라미터의 이름을 물어봅니다.
