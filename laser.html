Tracking to Laser

A camera finds people on a floor. TouchDesigner turns their positions into vector shapes. A 10 W RGB laser draws the shapes on the same floor.

Status

I built this system between 2026-09-27 and 2026-10-31 and ran it on a real floor with the real laser. The tracking-driven patterns were cancelled before the performance because the laptop could not hold its charge.

Signal path

   |
   v
 TouchDesigner sends frames to the detector
   |
   v
 Detector process: YOLO11n person boxes
   |
   v
 TouchDesigner: blob tracking on the floor
   |
   v
 Phase logic: line shapes on an 8 x 8 grid
   |
   v
 Laser mapping and point output
   |
   v
 Helios DAC > ILDA > X-RAW10 laser
  • Camera. The colour camera replaced depth, which stops at 5.46 m. Recorded takes play through the whole system, so most work needed no sensor.
  • Detection. A separate GPU process finds people in 7 to 9 ms per frame and sends boxes back over UDP.
  • Tracking. The system removes duplicate boxes, finds the feet, maps them to the floor, and drops anyone off the board. A tracker and a One Euro filter give up to 8 stable positions. Tuning removed all position jumps over 0.1 floor units in a 1999-frame test take.
  • Shapes. A laser cannot fill areas, so 18 phases draw outlines. A macro pad and one control panel run the system with no network.
  • Output. TouchDesigner sends 20 000 points per second to the Helios DAC. Colour thresholds keep white correct at low power.

Automatic mapping

The camera is the measuring tool, so the laser needs no manual alignment.

  1. Camera to floor. One button finds the 8 x 8 floor board and fits lens distortion and perspective. Accuracy was 0.025 to 0.029 tile, in about 20 s.
  2. Laser to floor. The laser draws 10 test lines, one at a time. The camera finds each line, and the system solves the corner pin and the bend of the scan mirrors. A bad result is not applied.
  3. Verify. The laser draws 10 straight floor lines. The camera measures the error, and the system keeps a correction only if it measures better.
  4. Mirror speed. Three test squares fit a mirror model for sharper corners. The real speed is not settled: runs gave 1680 to 2125 Hz.

Seven real mapping runs took place on 2026-10-31. Five were not applied, and each of these added a check to the system. Causes included a moving person, a darker room, and a slow camera image. The final run found 9 of 10 lines with an error of 0.020 laser units. Verification reduced the rms error from 0.54 to 0.15 tile.

Tests

The logic is in plain Python modules, so tests run with no TouchDesigner, camera, or laser.

Benches tested mirror behaviour against 90 simulated models. Recorded takes then tested the full live system. On the floor, an event log and a check image for each mapping run recorded the results.

Failure handling

  • If the Kinect leaves USB, the system holds positions and reconnects. This recovered from a real loss.
  • If TouchDesigner hangs, an outside process shows an alert. In a test, it fired at 4.3 s.
  • If the macro pad loses its keys, the system writes them again.
  • If the detector stops, the system restarts it.

First version: a stage system for four dancers

The first version of the show used a projector, not a laser, and no tracking. The floor was the display. Each of four dancers got a lane of light that travelled their path. The four danced the same phrase with a time offset, so the light had to make the same offset.

It ran in TouchDesigner, but scripts built the node network. The source was code on disk, so it was possible to review it, compare versions, and let a model drive it.

The choreography came as a handwritten notebook. It became about 130 small grid images, one for each dancer and phrase. The colour of a cell gave its meaning: red start, yellow path, green end, white accent. A scanner changed each grid into a distance field (how far each cell is along the path) and baked all of them into the shader. The path search happened once, at build time; each frame only looked up the result.

 notebook --scan--> grids --distance field--> baked data --> shader

 render      stateless: no feedback buffer, one lookup per pixel
 offset      stored as a phase value per pattern, so the canon is data
 sequencer   four lanes on absolute time; blocks snap, cut and save as JSON
 continuity  a pattern is offered only if its start matches the last one's end
 output      corner-pin warp onto the real floor

Because the render has no state, nothing builds up and nothing drifts over a long show. Any moment can be rendered directly, so the transport can scrub. A bridge let a model drive the running session and read back a screenshot, so each interface change was checked by looking at it.

Status: the tool was built, but the evening was not sequenced. Two of twenty-four rows existed as arrangements, and this version was never performed. The next version replaced the projector with the laser and added the tracking described above.

트래킹 투 레이저

카메라가 바닥 위의 사람을 찾습니다. TouchDesigner가 그 위치를 벡터 도형으로 바꾸고, 10 W RGB 레이저가 같은 바닥 위에 그 도형을 그립니다.

상태

2026-09-27부터 2026-10-31까지 이 시스템을 만들었고, 실제 바닥에서 실제 레이저로 운영했습니다. 트래킹으로 움직이는 패턴은 노트북 배터리가 버티지 못해 공연 직전에 취소되었습니다.

  • 카메라. 깊이 센서는 5.46 m까지만 측정되어 컬러 카메라로 바꿨습니다. 녹화한 테이크를 전체 시스템에 그대로 재생할 수 있어서, 대부분의 작업은 센서 없이 진행했습니다.
  • 검출. 별도의 GPU 프로세스가 프레임당 7~9 ms 안에 사람을 찾고, UDP로 박스를 돌려보냅니다.
  • 트래킹. 중복 박스를 지우고, 발 위치를 찾아 바닥 좌표로 옮기고, 보드 밖의 사람은 제외합니다. 트래커와 One Euro 필터로 최대 8명의 위치를 안정적으로 유지합니다. 튜닝 후 1999프레임 테스트 테이크에서 0.1 바닥 단위를 넘는 위치 튐이 모두 사라졌습니다.
  • 도형. 레이저는 면을 채울 수 없으므로 18개의 페이즈가 외곽선을 그립니다. 매크로 패드와 컨트롤 패널 하나로 네트워크 없이 시스템을 운영합니다.
  • 출력. TouchDesigner가 초당 20 000개의 점을 Helios DAC로 보냅니다. 색상 임계값으로 낮은 출력에서도 흰색을 정확하게 유지합니다.

자동 매핑

카메라가 측정 도구 역할을 하므로 레이저를 손으로 정렬할 필요가 없습니다.

  1. 카메라에서 바닥으로. 버튼 하나로 8 x 8 바닥 보드를 찾고, 렌즈 왜곡과 원근을 맞춥니다. 정확도는 0.025~0.029 타일, 소요 시간은 약 20초입니다.
  2. 레이저에서 바닥으로. 레이저가 테스트 선 10개를 하나씩 그립니다. 카메라가 각 선을 찾고, 시스템이 코너 핀과 스캔 미러의 휨을 계산합니다. 나쁜 결과는 적용하지 않습니다.
  3. 검증. 레이저가 바닥에 직선 10개를 그립니다. 카메라가 오차를 측정하고, 측정값이 더 좋아질 때만 보정을 유지합니다.
  4. 미러 속도. 테스트 사각형 3개로 미러 모델을 맞춰 모서리를 더 선명하게 합니다. 실제 속도는 아직 확정되지 않았습니다. 실행마다 1680~2125 Hz가 나왔습니다.

2026-10-31에 실제 매핑을 7번 실행했습니다. 5번은 적용되지 않았고, 그때마다 시스템에 검사가 하나씩 추가되었습니다. 원인은 움직이는 사람, 더 어두운 방, 느린 카메라 영상 등이었습니다. 마지막 실행은 선 10개 중 9개를 찾았고 오차는 0.020 레이저 단위였습니다. 검증으로 rms 오차가 0.54에서 0.15 타일로 줄었습니다.

장애 처리

  • Kinect가 USB에서 빠지면 위치를 유지하고 다시 연결합니다. 실제로 연결이 끊겼을 때 복구되었습니다.
  • TouchDesigner가 멈추면 외부 프로세스가 경고를 띄웁니다. 테스트에서는 4.3초에 작동했습니다.
  • 매크로 패드의 키 설정이 사라지면 시스템이 다시 씁니다.
  • 검출기가 멈추면 시스템이 다시 시작합니다.

첫 번째 버전: 네 명의 무용수를 위한 무대 시스템

쇼의 첫 번째 버전은 레이저가 아닌 프로젝터를 썼고, 트래킹은 없었습니다. 바닥이 곧 디스플레이였습니다. 네 명의 무용수는 각자 자신의 경로를 따라 움직이는 빛의 레인을 받았습니다. 네 사람이 같은 프레이즈를 시간차를 두고 추었기 때문에, 빛도 같은 시간차를 만들어야 했습니다.

TouchDesigner에서 실행되었지만 노드 네트워크는 스크립트가 만들었습니다. 원본이 디스크의 코드였기 때문에 검토하고, 버전을 비교하고, 모델이 직접 조작할 수 있었습니다.

안무는 손으로 쓴 노트로 전달되었습니다. 이것이 무용수와 프레이즈마다 하나씩, 약 130개의 작은 그리드 이미지가 되었습니다. 셀의 색이 의미를 나타냅니다: 빨강은 시작, 노랑은 경로, 초록은 끝, 흰색은 강조입니다. 스캐너가 각 그리드를 거리 필드(각 셀이 경로를 따라 얼마나 떨어져 있는지)로 바꾸고, 전부를 셰이더에 구워 넣었습니다. 경로 탐색은 빌드할 때 한 번만 하고, 각 프레임은 결과를 조회하기만 합니다.

렌더에 상태가 없기 때문에 긴 공연 동안에도 쌓이는 것도, 어긋나는 것도 없습니다. 어느 순간이든 바로 렌더할 수 있어서 타임라인을 자유롭게 앞뒤로 움직일 수 있습니다. 브리지를 통해 모델이 실행 중인 세션을 조작하고 스크린샷을 다시 읽을 수 있었기 때문에, 인터페이스의 모든 변경을 눈으로 보고 확인했습니다.

상태: 도구는 완성되었지만 공연 전체의 시퀀스는 만들지 못했습니다. 스물네 줄 중 두 줄만 편곡되었고, 이 버전은 공연되지 않았습니다. 다음 버전에서 프로젝터를 레이저로 바꾸고 위에서 설명한 트래킹을 추가했습니다.
